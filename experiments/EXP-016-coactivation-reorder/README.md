## Research question

In the historical Qwen3-30B Q4_K_M mmap setup, did the specific co-activation-based GGUF reorder produced from `route.log` improve generation throughput?

*(Original wording, kept as history: "Does placing co-activated experts contiguously on disk speed up mmap streaming?")*

## Hypothesis

[HYPOTHESIS] Co-activation-ordered layout turns random reads into longer sequential runs and raises throughput.

*Audit reading (2026-10-11):*
- **What failed.** The throughput-improvement prediction failed for the specific historical layout and the tested setup. FALSIFIED applies to that operational historical prediction.
- **What it does not establish:**
  - that physical layout never matters;
  - that co-activation information cannot be useful;
  - that another reorder objective, a different router trace, or a different workload or model would fail;
  - that explicit-read Expert Store / PSXS physical placement would fail.

## Setup

`argine reorder` from the router log (route.log), then benchmark of original vs reordered GGUF (mmap path, 8 threads).

*Audited setup (2026-10-11), from `raw/records.jsonl`:*
- **Model.** Qwen3-30B-A3B Q4_K_M (48 layers, 128 experts per layer, 8 active per token).
- **Reorder event.** One historical router trace, `route.log`. The reorder event (2026-09-27 20:58:06) created `Qwen_Qwen3-30B-A3B-Q4_K_M-reordered.gguf`, rewriting 192 tensors and 17,603,493,888 bytes.
- **Benchmarks.** The plan used the CPU backend, 8 threads, ctx 4096 and 128 generated tokens, with 3 repetitions inside each invocation. Binary label `PICOSTAR_LLAMA_DIR` (the old build, not fingerprinted).
- **Condition attribution.** Original vs reordered is not encoded independently in the raw benchmark records: all three selected benchmark records carry the base model path `Qwen_Qwen3-30B-A3B-Q4_K_M.gguf`.
- **Execution order** is known only from the timestamps (21:00:10, 22:45:03, 22:47:14). No condition rotation or randomized order is recorded.

## Interpretation

*[Historical interpretation, narrowed by the 2026-10-11 audit: "Reordering made it slower. Later work showed the access path (page faults) dominated, not seek patterns." This is superseded by the wording below.]*

[FALSIFIED, HISTORICAL / ATTRIBUTION-LIMITED] **Audit closure (2026-10-11).**
- FALSIFIED is retained, with historical-attribution and tested-layout scope.
- According to the contemporaneous historical condition attribution, the specific co-activation-based GGUF reorder produced by the historical `argine reorder` workflow did not show the predicted throughput improvement: the reordered condition was slower in that comparison (4.69 vs 5.17 tok/s).
- No universal negative claim is made about co-activation-based layout, all MoE models, workloads, storage or access paths, mmap implementations, or physical expert placement in general.
- Later Argine measurements showed that, on the reference machine and tested access pattern, the mmap page-fault path was substantially slower than explicit reads (≈310 MB/s vs ≈1324 MB/s, EXP-003). This provides context for why layout locality may not have dominated performance, but it does not causally establish why the reorder failed.
- No rerun is required for historical closure ([historical audit](../../docs/research/HISTORICAL-AUDIT-EXP011-018.md)).

## Limitations

[LIMITATION] The raw benchmark records do not label which file was used in every run; attribution from Argine's README.

[LIMITATION, historical audit 2026-10-11]
1. One historical model: Qwen3-30B-A3B Q4_K_M.
2. One reorder, generated from one preserved `route.log`.
3. One historical reorder algorithm/objective.
4. The original vs reordered benchmark attribution comes from the README, not independently from raw benchmark metadata.
5. The historical 4.69 value is a within-invocation repetition; the corresponding selected raw group's median is 4.57.
6. Three benchmark groups are included by timestamp in the builder, but their exact roles in the comparison are not independently encoded.
7. No condition rotation or randomized launch order is preserved.
8. The baseline 21:00 run and the later 22:45 / 22:47 groups are separated in time; they are not an interleaved paired experiment.
9. Dynamic RAM availability and planner expert-cache budgets differ slightly across the selected records (7.29–7.56 GB expert cache).
10. Historical binary identity is not fingerprinted to the modern Argine2 standard (label `PICOSTAR_LLAMA_DIR`).
11. One prompt / historical benchmark workload.
12. This is an mmap-era result; it does not directly test the later explicit-read Expert Store / PSXS physical-placement problem.
13. No independent causal experiment separates layout locality from page-fault overhead.
14. The semantics of `runs_prima` / `runs_dopo` are not sufficiently documented to rename them "mean run length".
