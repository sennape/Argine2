## Research question

How much does the build of llama.cpp matter for speed on this machine?

## Hypothesis

[HYPOTHESIS] (implicit before) The binary does not matter, only the algorithm.

*Audit reading (2026-10-11):* the operational claim tested is "binary identity can be ignored when comparing performance; only the nominal algorithm/configuration matters".

## Setup

Qwen3-30B-A3B IQ2_S fully resident, 4 threads, 3 repetitions: official b11214, old patched build (OpenMP, dynamic), new patched build (newer llama.cpp, no OpenMP, static).

*Audit note (2026-10-11), from `raw/records.jsonl`:*
- The three records share the same model file (10,289,713,824 bytes), CPU backend, 4 threads, `n_predict` 128, prompt length and recorded runtime plan. The plans are identical apart from their free-text `decisions` notes.
- Within the recorded model/runtime configuration, the principal recorded experimental difference is `runtime.build`: `b11214`, `PICOSTAR_LLAMA_DIR` (old patched; no version or commit recorded) and `llama-noomp@757a17a4` (new patched). The invocations were sequential rather than interleaved, so unmeasured session state is not controlled.
- Each build is one `argine benchmark` invocation with 3 repetitions inside it. The invocations ran sequentially, 19:41 → 20:22.
- The two patched binaries differ in llama.cpp source version, OpenMP configuration and linkage, so the source is **not** the same.

argine benchmark qwen30b-IQ2S.gguf --threads 4

## Raw data

`raw/records.jsonl` — the exact records of Argine's `runs.jsonl` used here (sanitised: host and user name only). Full log: `data/raw/argine-v1/runs.jsonl`. `results.csv` is regenerated by `python tools/build_historical_data.py`.

## Result

[MEASURED] official b11214 13.53 tok/s (median); old patched 7.45; new patched (noomp@757a17a4) 12.97.

## Interpretation

[DERIVED] 1.74x between two builds of (nearly) the same source. Every comparison in Argine2 must therefore hold the binary fixed and record its fingerprint (section 28). Whether OpenMP or the llama.cpp version is responsible was not isolated. *[Narrowed by the 2026-10-11 audit, below: "(nearly) the same source" is not established.]*

[SUPPORTED, HISTORICAL] **Audit closure (2026-10-11).**
- [DERIVED] Under the matched recorded model/runtime plan, the old patched and new patched binaries differ by 1.74x in median generation throughput (7.45 vs 12.97 tok/s).
- This shows that binary identity must be treated as an experimental variable and fingerprinted.
- It does not isolate a causal build flag: llama.cpp version, OpenMP configuration and linkage differ between the binaries. The result is **not** attributed to OpenMP, static linking, a compiler option or recompilation alone.
- **Corroborative:** the official b11214 binary gave 13.53 tok/s, close to the new patched 12.97 and far above the old patched 7.45.
- No rerun is required for closure ([historical audit](../../docs/research/HISTORICAL-AUDIT-EXP011-018.md)).

## Limitations

[LIMITATION] OpenMP and llama.cpp version are confounded.

[LIMITATION, historical audit 2026-10-11]
- **Confounded build differences.** The llama.cpp source/version, OpenMP and linkage/build configuration all differ between the patched binaries. The old patched binary is identified only by the `PICOSTAR_LLAMA_DIR` label, with no version, commit or hash in the record.
- **Repetitions.** The three repetitions are inside each benchmark invocation. They are not three independent or interleaved launches, and the builds ran in sequence.
- **Protocol era.** The experiment predates Argine2's reproducibility protocol (binary fingerprints, rotated launches).
- **Between-session variation.** EXP-018 later measured meaningful between-session variation. 1.74x is an observed historical contrast on this machine and configuration, not a universal build-effect coefficient.
- **No causal attribution.** Attributing the gap to one compiler or build option is not supported.
