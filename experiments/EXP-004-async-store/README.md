## Research question

Do overlapped (asynchronous) reads improve generation speed, and uniformly across budgets?

## Hypothesis

[HYPOTHESIS] (first published) Asynchronous reads improve speed by 7-11% uniformly. [HYPOTHESIS] (tested here) The gain grows with miss pressure, because more misses per node means more reads in flight and NVMe throughput rises with queue depth.

## Setup

Qwen3-30B-A3B Q4_K_M + expert store, 4 threads, one binary (llama-noomp@3cac5531), budgets 4/3/2/1.5 GiB, three read modes per budget (`sincrono`, `blocco:2`, `asincrono` = emit-and-continue), 3 repetitions each. Within each budget the modes ran in the **fixed order** sync → block-2 → async; the order was not rotated or interleaved (`processed/notes.json`). [Corrected 2026-10-11: this sentence previously read "modes alternated inside each budget".]

## Result

[MEASURED] median tok/s (sync / block-2 / emit-and-continue): 4 GiB 6.37 / 6.23 / 6.33; 3 GiB 4.98 / 4.89 / 5.19; 2 GiB 4.10 / 4.09 / 4.30; 1.5 GiB 3.51 / 3.52 / 3.89.

[DERIVED] emit-and-continue vs sync: -0.6% at 4 GiB, +4.2%, +4.9%, +10.8% at 1.5 GiB. Block-2 is indistinguishable from sync at every budget.

## Interpretation

[DERIVED] The benefit is regime-dependent: zero where hits dominate, ~11% under strong miss pressure. The earlier '+7-11% uniformly' compared three different binaries and attributed a 4-5% build difference to the algorithm.

[SUPPORTED, with limitation] **Audit closure (2026-10-11).** Asynchronous issue-and-continue reads improved throughput under stronger miss pressure, with little or no benefit at high residency. Configurations ran in a fixed within-budget order rather than a rotated or interleaved order, so session and thermal order effects cannot be fully excluded. No rerun is required for closure. A rotated replication would be useful only if this finding becomes central to the final paper ([historical audit](../../docs/research/HISTORICAL-AUDIT-EXP001-006.md)).

## Limitations

[LIMITATION] Mode order is the same at every budget (sync, block, async), not rotated. Queue depth in Argine v1 was a wait-derived PROXY ((ns_read/wall) x (reads/blocks)); Q(t) from per-request timestamps requires the Argine2 instrumentation (EXP-007); it is exact only when every completion timestamp is exact.
