## Research question

Does llama.cpp's SIMD repack (an extra interleaved copy of quantised weights) pay off on this CPU?

## Hypothesis

[HYPOTHESIS] Repacking speeds up matrix kernels at a memory cost (~2/3 of the weights on Q4).

## Setup

Dense Qwen3-8B Q4_K_M, official b11214, 8 threads, 3 repetitions per configuration, repack ON then OFF.

## Commands

```bat
argine benchmark Qwen3-8B-Q4_K_M.gguf --repack
argine benchmark Qwen3-8B-Q4_K_M.gguf
```

## Raw data

`raw/records.jsonl` — the exact records of Argine's `runs.jsonl` used here (sanitised: host and user name only). Full log: `data/raw/argine-v1/runs.jsonl`. `results.csv` is regenerated by `python tools/build_historical_data.py`.

## Result

[MEASURED] repack ON 7.64 / 7.34 / 7.05 tok/s, RAM peak 8.16 GiB; repack OFF 8.84 / 8.34 / 8.24 tok/s, RAM peak 5.04 GiB.

## Interpretation

[DERIVED] On this AVX2-only CPU repack is worse on both axes (slower and +3.1 GiB). Means: ON 7.34 tok/s, OFF 8.47 tok/s, so OFF is ≈15% faster. Argine disables it by default (except for shared tensors when the expert store is active, because `--no-repack` disables every extra buffer type, the store included).

[SUPPORTED, HISTORICAL] **Audit closure (2026-10-11).** On the tested AVX2-only i5-1340P configuration and the tested llama.cpp build (official b11214, dense Qwen3-8B Q4_K_M), repack increased memory usage and did not improve throughput. Repack is **not** claimed to be harmful in general, or slower on every CPU, build or model. No rerun is required for closure ([historical audit](../../docs/research/HISTORICAL-AUDIT-EXP001-006.md)).

## Limitations

[LIMITATION] One run per configuration (AAA then BBB, not interleaved); one dense model; repetitions show a downward drift within each run (thermal), larger than the difference between the first repetitions. Thermal and session drift are therefore possible confounds of the speed difference; the memory difference does not depend on them.
