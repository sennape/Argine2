## Research question

How many generation threads maximise tokens/s on the i5-1340P (4 P-cores + 8 E-cores)?

## Hypothesis

[HYPOTHESIS] One thread per P-core is optimal: ggml synchronises all threads at every graph node, so an E-core (or an SMT sibling) adds a participant to every barrier without adding proportional work.

## Setup

`argine benchmark --sweep-threads`, 2-3 repetitions per point, sequential order. Four sweeps: dense Qwen3-8B Q4_K_M on the official llama.cpp b11214 (twice); Qwen3-30B-A3B IQ2_XXS fully resident and Q4_K_M + expert store (6 GiB) on the OLD patched build (built with OpenMP, later shown to be 1.74x slower, EXP-011).

## Commands

```bat
argine benchmark MODEL --sweep-threads 4,6,8,12
```

## Raw data

`raw/records.jsonl` — the exact records of Argine's `runs.jsonl` used here (sanitised: host and user name only). Full log: `data/raw/argine-v1/runs.jsonl`. `results.csv` is regenerated by `python tools/build_historical_data.py`.

## Result

[MEASURED] 30B MoE, old OpenMP build: 4 threads 7.08 tok/s > 6: 5.19 > 8: 4.84 > 12: 4.01 (IQ2_XXS); with the store 4 threads 5.93 vs 8 threads 4.23 (+40%).

[MEASURED] Dense 8B, official build: the ordering is the opposite — 4 threads 6.11 / 6.65, 8 threads 6.82 / 7.14, 12 threads 6.81 / 7.23 tok/s (two sweeps).

## Interpretation

[DERIVED] The +40-46% of Argine's README holds for the MoE on the OpenMP build. It does not generalise to the dense model on the official build, where more threads were faster. The barrier explanation predicts a build dependence (OpenMP barriers vs ggml's own), which is consistent with both observations but untested. The README stated the rule as general; the raw data limit it to the configuration where it was measured.

[INCONCLUSIVE] **Audit closure (2026-10-11).** The optimal generation thread count is build- and/or model-dependent. The historical evidence does not establish that one thread per P-core is optimal on the current Argine2 runtime. The measurements stay valid as measurements of the binaries used at the time. The experiment is historically closed as INCONCLUSIVE, with no rerun required for closure ([historical audit](../../docs/research/HISTORICAL-AUDIT-EXP001-006.md)). The open question (RQ-014) is a *future* experiment, a small interleaved thread sweep on the current binary; it does not reopen this one.

## Limitations

[LIMITATION] Never re-measured on the current non-OpenMP build that produced every later result. 2-3 repetitions, not interleaved. Different models on the two builds, so build and model are confounded.
